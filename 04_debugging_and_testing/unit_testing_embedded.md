# Unit Testing in Embedded Systems

## Prerequisites
- C programming: function pointers, structs, header files
- Basic understanding of hardware abstraction layers (HAL)
- Familiarity with make-based build systems

---

## Concept Reference

### Why Unit Testing Is Hard on Embedded Systems

Unit testing on a host PC is straightforward: compile, link, run, assert. Embedded systems introduce several obstacles:

```
Obstacle                     Problem                         Solution
---------------------------  ------------------------------  --------------------------
Target hardware dependency   Tests require specific MCU/FPGA  Hardware abstraction layer
Peripheral side effects      UART, GPIO, SPI not on host      Mock/stub the peripherals
Long build-deploy cycle      Flash programming takes time      Test on host, verify on target
No standard I/O              Can't printf results easily       Unity test runner + ITM/UART
Interrupts and timing        Real timing not reproducible      Fake time injection
Limited tooling              GDB/GCC not always available      arm-none-eabi-gcc + Unity
```

The fundamental strategy is: **separate hardware-dependent code from logic-dependent code**, then test the logic on the host machine where all standard testing tools are available.

### Unity Test Framework

Unity is a minimal C unit test framework designed for embedded targets. It consists of three files: `unity.h`, `unity.c`, and `unity_internals.h`. No dynamic allocation, no C++ required.

```c
/* unity_example_test.c */
#include "unity.h"
#include "my_module.h"   /* the module under test */

/* setUp() is called before each test function */
void setUp(void) {
    my_module_init();    /* reset module state before each test */
}

/* tearDown() is called after each test function */
void tearDown(void) {
    /* cleanup if needed */
}

/* Test functions must start with "test" */
void test_add_two_positive_numbers(void) {
    TEST_ASSERT_EQUAL_INT(5, my_add(2, 3));
}

void test_add_negative_numbers(void) {
    TEST_ASSERT_EQUAL_INT(-1, my_add(2, -3));
}

void test_add_overflow(void) {
    /* INT32_MAX + 1 should saturate, not wrap */
    TEST_ASSERT_EQUAL_INT(INT32_MAX, my_add_saturating(INT32_MAX, 1));
}

/* Unity main runner (generated by Ruby script or written manually) */
int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_add_two_positive_numbers);
    RUN_TEST(test_add_negative_numbers);
    RUN_TEST(test_add_overflow);
    return UNITY_END();  /* returns 0 if all tests pass, 1 otherwise */
}
```

**Key Unity assertions:**

```c
/* Integer assertions */
TEST_ASSERT_EQUAL(expected, actual)
TEST_ASSERT_EQUAL_INT(expected, actual)
TEST_ASSERT_EQUAL_UINT32(expected, actual)
TEST_ASSERT_EQUAL_HEX32(expected, actual)  /* displays as hex on failure */

/* Boolean assertions */
TEST_ASSERT_TRUE(condition)
TEST_ASSERT_FALSE(condition)
TEST_ASSERT_NULL(pointer)
TEST_ASSERT_NOT_NULL(pointer)

/* Float / double */
TEST_ASSERT_FLOAT_WITHIN(delta, expected, actual)

/* Array comparison */
TEST_ASSERT_EQUAL_MEMORY(expected, actual, length)
TEST_ASSERT_EQUAL_INT_ARRAY(expected, actual, num_elements)

/* Explicit failure */
TEST_FAIL_MESSAGE("This code path should not be reached")

/* Skip a test (useful for platform-conditional tests) */
TEST_IGNORE_MESSAGE("Not implemented on this platform")
```

### CMock — Automatic Mock Generation

CMock reads C header files and generates mock implementations of every function declared in the header. The generated mocks:
- Record whether the function was called
- Verify the arguments passed to it
- Return a specified value

```
Build flow with CMock:

  hal_uart.h  ─────────────────────────────────────┐
  (header with function declarations)               │
                                                    ▼
                                             CMock (Ruby script)
                                                    │
                                          generates │
                                                    ▼
                                         mock_hal_uart.h
                                         mock_hal_uart.c   ──── compiled into test
                                         (recording stubs)       executable

  my_driver.c ──────────────────────────────────────── compiled into test executable
  (code under test, calls hal_uart_write() etc.)

  test_my_driver.c ─────────────────────────────────── compiled into test executable
  (test code: sets up expectations, calls driver functions, verifies results)
```

### Hardware Abstraction Layer (HAL) Design for Testability

The critical architectural decision: every hardware operation must go through a function pointer or a thin HAL layer, not direct register access.

**Untestable design (register access in business logic):**

```c
/* sensor_driver.c -- HARD TO TEST: reads hardware directly */
float read_temperature(void) {
    /* Waits for ADC conversion -- cannot simulate on host */
    while (!(ADC1->SR & ADC_SR_EOC)) {}
    uint16_t raw = ADC1->DR;
    return (raw * 3.3f / 4096.0f - 0.5f) / 0.01f;  /* conversion formula */
}
```

**Testable design (HAL injection):**

```c
/* hal_adc.h -- Hardware Abstraction Layer interface */
typedef struct {
    uint16_t (*read_raw)(uint8_t channel);
    void     (*start_conversion)(uint8_t channel);
    bool     (*is_conversion_complete)(uint8_t channel);
} HalAdc_t;

/* sensor_driver.h */
typedef struct {
    const HalAdc_t *adc;
    uint8_t         channel;
} SensorDriver_t;

/* sensor_driver.c -- TESTABLE: uses injected HAL */
float sensor_read_temperature(const SensorDriver_t *drv) {
    drv->adc->start_conversion(drv->channel);
    while (!drv->adc->is_conversion_complete(drv->channel)) {
        /* In real firmware: yield or timeout.
           In tests: fake HAL returns immediately. */
    }
    uint16_t raw = drv->adc->read_raw(drv->channel);
    return (raw * 3.3f / 4096.0f - 0.5f) / 0.01f;
}

/* hal_adc_real.c -- actual hardware implementation, not compiled in tests */
static uint16_t real_read_raw(uint8_t channel) {
    return ADC1->DR;
}
/* ... other real implementations ... */

const HalAdc_t HAL_ADC_REAL = {
    .read_raw              = real_read_raw,
    .start_conversion      = real_start_conversion,
    .is_conversion_complete = real_is_conversion_complete,
};
```

**test_sensor_driver.c:**

```c
#include "unity.h"
#include "sensor_driver.h"
#include "mock_hal_adc.h"   /* CMock-generated */

static SensorDriver_t test_sensor;

void setUp(void) {
    /* CMock-generated: sets up mock infrastructure */
    mock_hal_adc_Init();

    /* Construct a mock HAL -- CMock populates function pointers */
    static HalAdc_t mock_adc = {
        .read_raw               = mock_hal_adc_read_raw,
        .start_conversion       = mock_hal_adc_start_conversion,
        .is_conversion_complete = mock_hal_adc_is_conversion_complete,
    };
    test_sensor.adc     = &mock_adc;
    test_sensor.channel = 0;
}

void tearDown(void) {
    mock_hal_adc_Verify();   /* fail if expected calls not made */
    mock_hal_adc_Destroy();
}

void test_temperature_conversion_at_zero_celsius(void) {
    /* 0 degC corresponds to 0.5 V output => raw ADC value = 0.5/3.3 * 4096 = 620 */
    hal_adc_start_conversion_Expect(0);          /* expect start_conversion(channel=0) */
    hal_adc_is_conversion_complete_ExpectAndReturn(0, true);  /* returns immediately */
    hal_adc_read_raw_ExpectAndReturn(0, 620);    /* returns raw value for 0 degC */

    float temp = sensor_read_temperature(&test_sensor);

    TEST_ASSERT_FLOAT_WITHIN(0.5f, 0.0f, temp);
}

void test_temperature_conversion_at_25_celsius(void) {
    /* 25 degC: V = 0.5 + 25*0.01 = 0.75 V => raw = 0.75/3.3 * 4096 = 931 */
    hal_adc_start_conversion_Expect(0);
    hal_adc_is_conversion_complete_ExpectAndReturn(0, true);
    hal_adc_read_raw_ExpectAndReturn(0, 931);

    float temp = sensor_read_temperature(&test_sensor);

    TEST_ASSERT_FLOAT_WITHIN(0.5f, 25.0f, temp);
}
```

### Build System Integration

A typical project structure separating production code from test code:

```
project/
├── src/
│   ├── sensor_driver.c       <- code under test
│   ├── sensor_driver.h
│   ├── hal_adc_real.c        <- real hardware implementation
│   └── hal_adc.h             <- HAL interface (CMock processes this)
├── test/
│   ├── test_sensor_driver.c  <- Unity + CMock tests
│   └── support/
│       ├── mock_hal_adc.c    <- CMock-generated (do not edit)
│       └── mock_hal_adc.h    <- CMock-generated (do not edit)
├── vendor/
│   ├── unity/
│   │   ├── unity.c
│   │   └── unity.h
│   └── cmock/
│       ├── cmock.c
│       └── cmock.h
└── Makefile
```

**Makefile fragment for host-based testing:**

```makefile
CC       = gcc              # host compiler for tests (not arm-none-eabi-gcc)
CFLAGS   = -Wall -Wextra -I src/ -I vendor/unity/ -I vendor/cmock/ -I test/support/

TEST_SRCS = test/test_sensor_driver.c \
            src/sensor_driver.c \
            test/support/mock_hal_adc.c \
            vendor/unity/unity.c \
            vendor/cmock/cmock.c

test_sensor: $(TEST_SRCS)
    $(CC) $(CFLAGS) $^ -o $@ -lm
    ./$@                    # run tests immediately after build

# Generate mocks (requires Ruby + CMock gem)
test/support/mock_hal_adc.c test/support/mock_hal_adc.h: src/hal_adc.h
    ruby vendor/cmock/scripts/create_mock.rb $<
    mv mock_hal_adc.c mock_hal_adc.h test/support/
```

## Tier 1 — Fundamentals

### Question F1
**What is a mock object and how does it differ from a stub? Give an embedded example of each.**

**Answer:**

**Stub:** A minimal replacement for a dependency that returns hardcoded or configurable values without tracking how it was called. A stub allows the code under test to run but makes no assertions about the interaction.

```c
/* Stub: always returns a fixed sensor value, no tracking */
uint16_t hal_adc_read_raw(uint8_t channel) {
    (void)channel;   /* ignore which channel was requested */
    return 512U;     /* always return mid-scale */
}

/* Use: allows sensor_read_temperature() to complete without real hardware.
   Does NOT verify that channel 0 specifically was read. */
```

**Mock:** A replacement that records calls and verifies them against expectations. A mock will fail the test if an expected call is not made, or if it is called with wrong arguments.

```c
/* Mock: generated by CMock from hal_adc.h */

/* In test setup: set expectation */
hal_adc_read_raw_ExpectAndReturn(0, 512U);
/* Expectation: hal_adc_read_raw MUST be called with channel=0,
   and the mock will return 512U.
   If the function is called with channel=1, the test FAILS immediately.
   If the function is never called, the test FAILS in tearDown(). */
```

**When to use each:**

| Situation | Use |
|-----------|-----|
| You only need the dependency to "not crash" | Stub |
| You need to verify the code calls the right hardware sequence | Mock |
| Testing a function that converts data (no hardware calls expected) | Neither -- pure unit test |
| Reproducing specific hardware error conditions (I2C NACK) | Mock with ExpectAndReturn(ERROR) |

### Question F2
**Why is it important to test on the host machine rather than the target for most unit tests? What tests should still run on-target?**

**Answer:**

**Why test on host:**

1. **Speed:** Host compilation and test execution takes seconds. Flashing a target takes 10-60 seconds. Running a full test suite of 100 tests on host: ~1 second. On target: 10+ minutes.

2. **Tooling:** AddressSanitizer, UBSan, Valgrind, gcov code coverage — all available on host. These tools find memory errors that would manifest as silent corruption or random crashes on target.

3. **Isolation:** Tests on host use mock hardware, making each test deterministic. On-target tests depend on real hardware state (what if the sensor is unplugged?).

4. **Continuous integration:** Host-based tests run in CI pipelines (GitHub Actions, Jenkins). Most CI environments do not have embedded hardware attached.

5. **Debuggability:** Segfaults on host produce stack traces. HardFaults on target require JTAG.

**Tests that should run on-target:**

```
1. Hardware driver integration tests:
   Verify that the real HAL implementation correctly talks to real peripherals.
   Example: send known bytes via real UART, verify loopback received correctly.

2. Real-time behaviour:
   Tests that verify timing constraints (interrupt latency, DMA throughput).
   Timing on a host simulator does not represent target timing.

3. Memory layout verification:
   Confirm that the linker script correctly places sections.
   Stack and heap sizes correct for the production build.

4. Power consumption:
   Only measurable with real hardware and a power analyser.

5. Endurance / stress tests:
   Running continuously for 48+ hours to expose sporadic failures.
   Not practical on host where mocks would hide real hardware faults.
```

**Rule of thumb:** Test the algorithm on host. Test the integration on target.

### Question F3
**What is dependency injection in the context of embedded firmware, and why does it improve testability?**

**Answer:**

Dependency injection means that a module does not create or access its dependencies (hardware peripherals, timers, communication interfaces) directly. Instead, the dependencies are passed in from outside — typically as function pointers, interface structs, or constructor parameters.

**Without dependency injection (tightly coupled):**

```c
/* pump_controller.c: creates its own hardware dependency */
void pump_set_speed(uint8_t percent) {
    /* Direct timer register access -- UNTESTABLE on host */
    TIM3->CCR1 = (percent * TIM3->ARR) / 100;
}
```

**With dependency injection (loosely coupled):**

```c
/* pwm_interface.h: defines what a PWM driver looks like */
typedef struct {
    void (*set_duty_cycle)(uint8_t channel, uint8_t percent);
    void (*enable)(uint8_t channel);
    void (*disable)(uint8_t channel);
} PwmDriver_t;

/* pump_controller.h */
typedef struct {
    const PwmDriver_t *pwm;
    uint8_t            pwm_channel;
    uint8_t            max_speed_percent;
} PumpController_t;

/* pump_controller.c: uses injected PWM driver */
void pump_set_speed(const PumpController_t *ctrl, uint8_t percent) {
    if (percent > ctrl->max_speed_percent) {
        percent = ctrl->max_speed_percent;
    }
    ctrl->pwm->set_duty_cycle(ctrl->pwm_channel, percent);
}
```

**Now in a test:**

```c
/* Fake PWM driver: records calls without touching hardware */
static uint8_t last_channel;
static uint8_t last_duty;

static void fake_set_duty(uint8_t channel, uint8_t percent) {
    last_channel = channel;
    last_duty    = percent;
}

void test_pump_limits_speed_to_maximum(void) {
    static PwmDriver_t fake_pwm = { .set_duty_cycle = fake_set_duty };
    PumpController_t ctrl = { .pwm = &fake_pwm, .pwm_channel = 2, .max_speed_percent = 80 };

    pump_set_speed(&ctrl, 100);   /* request 100%, expect clamped to 80% */

    TEST_ASSERT_EQUAL_UINT8(2,  last_channel);
    TEST_ASSERT_EQUAL_UINT8(80, last_duty);
}
```

The business logic (clamping speed to maximum) is fully tested without any hardware. The only untested path is `fake_set_duty` vs the real PWM register writes, which is verified separately in a hardware integration test.

## Tier 2 — Intermediate

### Question I1
**Your project uses a ring buffer for UART communication. Write a set of Unity unit tests that provide comprehensive coverage of the ring buffer module, including boundary conditions.**

**Answer:**

```c
/* ring_buffer.h -- interface under test */
#ifndef RING_BUFFER_H
#define RING_BUFFER_H

#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

typedef struct {
    uint8_t  *data;
    size_t    capacity;   /* must be power of two */
    size_t    head;       /* write index */
    size_t    tail;       /* read index */
} RingBuffer_t;

void    rb_init(RingBuffer_t *rb, uint8_t *buf, size_t capacity);
bool    rb_push(RingBuffer_t *rb, uint8_t byte);
bool    rb_pop(RingBuffer_t *rb, uint8_t *out);
bool    rb_is_empty(const RingBuffer_t *rb);
bool    rb_is_full(const RingBuffer_t *rb);
size_t  rb_count(const RingBuffer_t *rb);

#endif /* RING_BUFFER_H */
```

```c
/* test_ring_buffer.c */
#include "unity.h"
#include "ring_buffer.h"

#define TEST_BUF_SIZE  8U

static RingBuffer_t rb;
static uint8_t      buf[TEST_BUF_SIZE];

void setUp(void) {
    rb_init(&rb, buf, TEST_BUF_SIZE);
}

void tearDown(void) {
    /* nothing to clean up for a static ring buffer */
}

/* --- Empty state --- */

void test_new_buffer_is_empty(void) {
    TEST_ASSERT_TRUE(rb_is_empty(&rb));
}

void test_new_buffer_is_not_full(void) {
    TEST_ASSERT_FALSE(rb_is_full(&rb));
}

void test_new_buffer_count_is_zero(void) {
    TEST_ASSERT_EQUAL_size_t(0, rb_count(&rb));
}

void test_pop_from_empty_returns_false(void) {
    uint8_t out = 0xFF;
    bool    result = rb_pop(&rb, &out);
    TEST_ASSERT_FALSE(result);
    TEST_ASSERT_EQUAL_UINT8(0xFF, out);   /* out should be unmodified */
}

/* --- Push and pop --- */

void test_push_single_byte(void) {
    TEST_ASSERT_TRUE(rb_push(&rb, 0x42));
    TEST_ASSERT_FALSE(rb_is_empty(&rb));
    TEST_ASSERT_EQUAL_size_t(1, rb_count(&rb));
}

void test_push_then_pop_returns_same_byte(void) {
    rb_push(&rb, 0x42);
    uint8_t out;
    TEST_ASSERT_TRUE(rb_pop(&rb, &out));
    TEST_ASSERT_EQUAL_UINT8(0x42, out);
}

void test_fifo_order_maintained(void) {
    rb_push(&rb, 0x01);
    rb_push(&rb, 0x02);
    rb_push(&rb, 0x03);

    uint8_t out;
    rb_pop(&rb, &out); TEST_ASSERT_EQUAL_UINT8(0x01, out);
    rb_pop(&rb, &out); TEST_ASSERT_EQUAL_UINT8(0x02, out);
    rb_pop(&rb, &out); TEST_ASSERT_EQUAL_UINT8(0x03, out);
}

/* --- Full state --- */

void test_buffer_full_after_capacity_pushes(void) {
    for (size_t i = 0; i < TEST_BUF_SIZE - 1; i++) {
        /* Typical ring buffer: full when count == capacity - 1 (wastes one slot)
           OR: full when count == capacity (if using a counter, not head==tail) */
        rb_push(&rb, (uint8_t)i);
    }
    /* Check implementation-specific full condition */
    TEST_ASSERT_TRUE(rb_is_full(&rb));
}

void test_push_to_full_returns_false(void) {
    /* Fill the buffer */
    while (!rb_is_full(&rb)) {
        rb_push(&rb, 0xAA);
    }
    /* One more push should fail */
    TEST_ASSERT_FALSE(rb_push(&rb, 0xBB));
}

void test_push_to_full_does_not_overwrite_existing_data(void) {
    while (!rb_is_full(&rb)) {
        rb_push(&rb, 0x55);
    }
    rb_push(&rb, 0x99);   /* should silently fail */

    uint8_t out;
    while (!rb_is_empty(&rb)) {
        rb_pop(&rb, &out);
        TEST_ASSERT_EQUAL_UINT8(0x55, out);  /* no 0x99 should appear */
    }
}

/* --- Wrap-around (the critical boundary condition) --- */

void test_wrap_around_preserves_data(void) {
    /* Push 5 bytes, pop 4, push 5 more: forces head and tail to wrap */
    for (uint8_t i = 0; i < 5; i++) {
        rb_push(&rb, i);
    }
    for (uint8_t i = 0; i < 4; i++) {
        uint8_t out;
        rb_pop(&rb, &out);
        TEST_ASSERT_EQUAL_UINT8(i, out);
    }
    /* Push 5 more -- head must wrap around the end of the buffer array */
    for (uint8_t i = 10; i < 15; i++) {
        rb_push(&rb, i);
    }
    /* Buffer now contains: [4, 10, 11, 12, 13, 14] */
    uint8_t expected[] = {4, 10, 11, 12, 13, 14};
    for (size_t i = 0; i < sizeof(expected); i++) {
        uint8_t out;
        TEST_ASSERT_TRUE(rb_pop(&rb, &out));
        TEST_ASSERT_EQUAL_UINT8(expected[i], out);
    }
    TEST_ASSERT_TRUE(rb_is_empty(&rb));
}

/* --- Count tracking --- */

void test_count_reflects_pushes_and_pops(void) {
    TEST_ASSERT_EQUAL_size_t(0, rb_count(&rb));
    rb_push(&rb, 1); TEST_ASSERT_EQUAL_size_t(1, rb_count(&rb));
    rb_push(&rb, 2); TEST_ASSERT_EQUAL_size_t(2, rb_count(&rb));
    uint8_t out;
    rb_pop(&rb, &out); TEST_ASSERT_EQUAL_size_t(1, rb_count(&rb));
    rb_pop(&rb, &out); TEST_ASSERT_EQUAL_size_t(0, rb_count(&rb));
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_new_buffer_is_empty);
    RUN_TEST(test_new_buffer_is_not_full);
    RUN_TEST(test_new_buffer_count_is_zero);
    RUN_TEST(test_pop_from_empty_returns_false);
    RUN_TEST(test_push_single_byte);
    RUN_TEST(test_push_then_pop_returns_same_byte);
    RUN_TEST(test_fifo_order_maintained);
    RUN_TEST(test_buffer_full_after_capacity_pushes);
    RUN_TEST(test_push_to_full_returns_false);
    RUN_TEST(test_push_to_full_does_not_overwrite_existing_data);
    RUN_TEST(test_wrap_around_preserves_data);
    RUN_TEST(test_count_reflects_pushes_and_pops);
    return UNITY_END();
}
```

**Coverage analysis:** These tests cover empty/full boundary conditions, FIFO ordering, the wrap-around (the most common ring buffer bug), count tracking, and rejection of pushes to a full buffer. The one omission for discussion: thread-safety. Ring buffers used between ISRs and tasks require atomic operations on head/tail — this is a separate concern tested differently (testing with concurrent tasks or with explicit interrupt-disable wrappers).

### Question I2
**Describe how you would use CMock to test a module that reads from an I2C sensor. The module must handle both the success case and sensor timeout.**

**Answer:**

```c
/* i2c_hal.h -- interface CMock will generate mocks for */
#ifndef I2C_HAL_H
#define I2C_HAL_H

#include <stdint.h>
#include <stdbool.h>

typedef enum {
    I2C_STATUS_OK      = 0,
    I2C_STATUS_TIMEOUT = 1,
    I2C_STATUS_NACK    = 2,
} I2cStatus_t;

I2cStatus_t i2c_write(uint8_t addr, const uint8_t *data, uint8_t len);
I2cStatus_t i2c_read (uint8_t addr, uint8_t *data, uint8_t len);

#endif
```

```c
/* bmp280_driver.h -- sensor driver under test */
#ifndef BMP280_DRIVER_H
#define BMP280_DRIVER_H

#include "i2c_hal.h"
#include <stdbool.h>

#define BMP280_I2C_ADDR   0x76U
#define BMP280_REG_TEMP   0xFAU

typedef struct {
    int32_t temperature_cdegC;  /* temperature in 1/100 degrees Celsius */
    bool    valid;
} Bmp280Reading_t;

Bmp280Reading_t bmp280_read_temperature(void);

#endif
```

```c
/* bmp280_driver.c */
#include "bmp280_driver.h"
#include "i2c_hal.h"

Bmp280Reading_t bmp280_read_temperature(void) {
    Bmp280Reading_t result = { .valid = false };

    /* Step 1: write register address */
    uint8_t reg = BMP280_REG_TEMP;
    I2cStatus_t status = i2c_write(BMP280_I2C_ADDR, &reg, 1);
    if (status != I2C_STATUS_OK) {
        return result;   /* invalid reading */
    }

    /* Step 2: read 3 bytes of temperature data */
    uint8_t raw[3];
    status = i2c_read(BMP280_I2C_ADDR, raw, 3);
    if (status != I2C_STATUS_OK) {
        return result;
    }

    /* Step 3: convert BMP280 raw format to centidegrees */
    int32_t raw_temp = ((int32_t)raw[0] << 12)
                     | ((int32_t)raw[1] <<  4)
                     | ((int32_t)raw[2] >>  4);
    /* Simplified: assume factory trim constants (real driver uses calibration) */
    result.temperature_cdegC = (raw_temp / 16) - 2500;
    result.valid = true;
    return result;
}
```

```c
/* test_bmp280_driver.c */
#include "unity.h"
#include "mock_i2c_hal.h"        /* CMock-generated from i2c_hal.h */
#include "bmp280_driver.h"

void setUp(void) {
    mock_i2c_hal_Init();         /* initialise CMock infrastructure */
}

void tearDown(void) {
    mock_i2c_hal_Verify();       /* fail if expected calls were not made */
    mock_i2c_hal_Destroy();
}

/* --- Success case --- */

void test_read_temperature_success(void) {
    uint8_t expected_reg  = BMP280_REG_TEMP;
    uint8_t raw_bytes[3]  = {0x7E, 0xC0, 0x00};  /* raw value for ~25.0 degC */

    /* Expect: i2c_write called with address 0x76, register 0xFA, length 1 */
    i2c_write_ExpectWithArrayAndReturn(
        BMP280_I2C_ADDR,
        &expected_reg, 1,    /* data array and length */
        1,                   /* verify 1 element */
        I2C_STATUS_OK);

    /* Expect: i2c_read called with address 0x76, buffer length 3 */
    i2c_read_ExpectAndReturn(BMP280_I2C_ADDR, NULL, 3, I2C_STATUS_OK);
    /* Tell CMock to fill the output buffer with our test data */
    i2c_read_ReturnArrayThruPtr_data(raw_bytes, 3);

    Bmp280Reading_t reading = bmp280_read_temperature();

    TEST_ASSERT_TRUE(reading.valid);
    /* raw_temp = (0x7E << 12) | (0xC0 << 4) | 0x00 = 0x7EC00 = 519168
       temperature = 519168/16 - 2500 = 32448 - 2500 = 29948 centidegrees = ~299 degC
       NOTE: simplified formula; in practice use BMP280 calibration.
       For this test we just verify the formula is applied. */
    TEST_ASSERT_TRUE(reading.temperature_cdegC > 0);
}

/* --- Timeout on write --- */

void test_read_returns_invalid_on_write_timeout(void) {
    uint8_t reg = BMP280_REG_TEMP;
    i2c_write_ExpectWithArrayAndReturn(
        BMP280_I2C_ADDR, &reg, 1, 1, I2C_STATUS_TIMEOUT);
    /* Note: i2c_read is NOT expected -- driver should return early */

    Bmp280Reading_t reading = bmp280_read_temperature();

    TEST_ASSERT_FALSE(reading.valid);
}

/* --- Timeout on read --- */

void test_read_returns_invalid_on_read_timeout(void) {
    uint8_t reg = BMP280_REG_TEMP;
    i2c_write_ExpectWithArrayAndReturn(
        BMP280_I2C_ADDR, &reg, 1, 1, I2C_STATUS_OK);
    i2c_read_ExpectAndReturn(
        BMP280_I2C_ADDR, NULL, 3, I2C_STATUS_TIMEOUT);

    Bmp280Reading_t reading = bmp280_read_temperature();

    TEST_ASSERT_FALSE(reading.valid);
}

/* --- NACK from sensor --- */

void test_read_returns_invalid_on_sensor_nack(void) {
    uint8_t reg = BMP280_REG_TEMP;
    i2c_write_ExpectWithArrayAndReturn(
        BMP280_I2C_ADDR, &reg, 1, 1, I2C_STATUS_NACK);

    Bmp280Reading_t reading = bmp280_read_temperature();

    TEST_ASSERT_FALSE(reading.valid);
}
```

**What these tests verify:**
- Success path: correct I2C address and register byte used, valid reading returned
- Error handling: each I2C error code causes the driver to return `valid=false`
- Protocol sequence: write-before-read order enforced by CMock strict ordering
- No unexpected calls: if the driver called `i2c_read` after a write timeout, CMock would fail the test

## Tier 3 — Advanced

### Question A1
**Describe how you would set up continuous integration for an embedded firmware project, running unit tests on a host machine and integration tests on actual hardware. What are the trade-offs and failure modes to handle?**

**Answer:**

**CI pipeline architecture:**

```
Developer pushes commit to Git
         |
         v
CI server (GitHub Actions / Jenkins / GitLab CI)
         |
    +----+----+
    |         |
    v         v
Host tests   Target tests
(fast)       (slow, hardware-gated)

Host test job:
  1. Install arm-none-eabi-gcc, Ruby, Ceedling
  2. ceedling test:all          <- unit tests run on x86 host with mocks
  3. ceedling gcov:all          <- generate code coverage report
  4. Check coverage >= threshold (e.g., 80% line coverage)
  5. Run cppcheck / PC-lint static analysis
  6. If all pass: mark build as "unit tests passed"

Target test job (triggered on PR merge to main, or nightly):
  1. Build firmware: make all
  2. Connect to hardware test fixture via USB (J-Link, ST-Link)
  3. Flash firmware: JLinkExe -commandfile flash.jlink
  4. Run target-resident test binary:
       pyocd run --target stm32f4 --frequency 4000000 test_firmware.elf
  5. Collect test results via UART (Unity prints results to serial port)
       python collect_test_results.py --port /dev/ttyUSB0 --timeout 30
  6. Verify: "X tests, 0 failures" in output
```

**Infrastructure for target tests:**

```
Hardware CI requirements:
  - Target evaluation board connected to CI server via USB
  - Serial port connected (UART for Unity output)
  - Power control: CI can reset the board (USB power switch or GPIO-controlled relay)
  - Network isolation: prevent target from interfering with production if it is networked

Example hardware fixture setup:
  Target board: STM32 Nucleo-144
  Debug connection: ST-Link USB (on-board, direct to CI server)
  UART output: USB-UART cable on USART3 (PA10/PA9)
  Power reset: controlled via ST-Link nRST pin in pyocd

Typical YAML (GitHub Actions):
  target-test:
    runs-on: [self-hosted, hardware-stm32]  # self-hosted runner with hardware
    needs: host-tests
    steps:
      - uses: actions/checkout@v3
      - name: Build and flash
        run: |
          make TARGET=stm32f4 BUILD=test
          pyocd flash -t stm32f429zitx build/test_firmware.elf
      - name: Collect results
        run: python ci/collect_uart_results.py --timeout 60
        timeout-minutes: 2
```

**Failure modes and mitigation:**

```
1. Hardware hangs / infinite loop:
   Mitigation: hardware watchdog with short timeout in test build.
               CI script kills job and power-cycles board after timeout.

2. Serial port not responding (USB disconnect):
   Mitigation: CI checks USB enumeration before attempting connection.
               Alert on repeated hardware failures (may indicate board damage).

3. Test binary crashes (HardFault):
   Mitigation: HardFault handler writes fault info to backup SRAM,
               Unity runner prints "HardFault at 0x<PC>" before watchdog reset.
               CI script parses this output and reports which test triggered the fault.

4. Non-deterministic timing tests:
   Mitigation: run timing-sensitive tests 10x; report failure only if > 20% fail.
               Or: define timing tolerance bands instead of exact values.

5. Only one board available, multiple developers:
   Mitigation: queue CI target jobs (only one runs at a time).
               Or: use hardware emulator (QEMU for ARM) for basic integration,
               real hardware only for peripheral-specific tests.
```

**Trade-offs:**

| Aspect | Host tests | Target tests |
|--------|-----------|--------------|
| Speed | Seconds | Minutes |
| Hardware required | None | Yes (dedicated board) |
| Peripheral accuracy | Mocked (approximate) | Real |
| Timing accuracy | Not representative | Real |
| Maintenance | Low | High (hardware failures, firmware bricking) |
| Coverage of HAL | None | Full |

**Interview insight:** Most companies run both tiers. The practical answer interviewers want is: (1) separate the architecture to enable host testing, (2) host tests in CI on every commit, (3) target tests on PR merge or nightly, (4) always have a watchdog in the test firmware. Candidates who have actually set this up can speak to the hardware maintenance overhead, which is real and often underestimated.
